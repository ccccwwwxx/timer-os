# Timer OS · 时代系统

**语言：** [English](README.md) · 简体中文 · [日本語](README.ja.md) · [한국어](README.ko.md) · [Español](README.es.md)

> 过去可调用，现在可感知，未来可调度。

**Timer OS（时代系统）** 是一个以 **时间、注意力、上下文、认知与行动** 为核心，而不是以 App 和文件为核心的实验性操作系统。

“时代系统”强调的不只是计时，而是对连续时间中的历史、当前状态与未来行动进行组织和调度。

项目基于一个基本判断：如果物理空间是一种稀缺资源，那么 **注意力就是人的时间资源中最稀缺的部分**。因此，一个真正有价值的个人 AI 不应该只回答问题，而应该持续理解上下文、保存高价值历史、维护认知状态，并判断什么时候真正需要占用人的注意力。

Timer OS 不只面向人类。同一套架构也可以支持长期运行的具身智能体和机器人，使其具备持续感知、位置感知、自我模型维护、认知调度与行动规划能力。

## 理念背景：语言是思考的接口

Timer OS 从一个设计前提出发：**人类的思考建立在语言之上。**

这并不意味着所有认知都必须依赖语言。感知、情绪、直觉和运动控制可以先于语言或存在于显式语言之外。但人类大量的抽象、反思、规划、协作，以及把记忆和认知外化为可以传递的结构，都通过语言获得表达、传播和再加工的能力。

因此，语言承载的不只是句子，它还压缩承载了概念、关系、意图、判断和推理痕迹。这也是语言模型能够跨越大量认知任务工作的原因之一：语言是人类将思考外化后最通用的符号接口之一。

Timer OS 因此不把语音和文字仅仅视为“给 AI 的命令”，而是把它们视为持续演化认知过程留下的可观察痕迹。**Body** 捕获语言，并同时绑定时间、说话人、位置和物理上下文；**YIdui** 将这些痕迹整合为可持续维护的认知状态；**Scheduler** 决定什么时候调用历史、什么时候值得投入更深推理，以及什么时候应该把认知转化为行动。

在高带宽脑机接口真正成熟之前，语言仍然是连接生物认知与外部认知系统最现实、最通用的桥梁之一。Timer OS 要做的，是把这条原本间歇性的桥梁变成连续的。

## 系统架构

Timer OS 由四个概念层组成：

- **Body** —— 系统进入现实世界的物理接口。面向人的第一种参考形态是分离式耳机 + 智能充电仓；面向具身机器人时，Body 可以扩展到摄像头、麦克风、IMU、位置系统、力/力矩传感器、关节编码器、电机和其他物理 I/O。
- **External Brain（外置大脑）** —— 将连续经历转化为可调用上下文的认知与记忆子系统。
- **YIdui（意堆）** —— 外置大脑中的核心认知子系统，负责长期维护知识、认知状态以及由证据驱动的自我模型更新。
- **Timer OS Scheduler** —— 根据历史、当前状态和未来意图，对时间、注意力、认知和行动进行统一调度。

手机被刻意定义为 **显示与控制界面**，而不是系统中心。

```text
现实世界
   ↓
Body（感知 / 位置 / 边缘执行 / 暂存 / 长连接）
   ↓
Timer Event Stream
   ↓
External Brain
   └── YIdui（认知状态 / 记忆 / 自我模型更新）
   ↓
Timer Scheduler
   ↓
行动 / 未来注意力或运动资源分配
```

## 认知调度

随着大模型上下文处理逐步成为基础设施，Timer OS 将 **认知调度** 视为更高一层的系统问题：

- 哪些数据需要高频感知；
- 此刻应该调用哪些历史；
- 应该使用哪个模型、投入多深的推理；
- 当认知或策略冲突时，什么时候需要重新评估；
- 什么时候应该执行动作；
- 什么时候有资格打断人；
- 对具身系统而言，哪些传感、位置或电机状态变化应该抢占当前计划。

Timer OS 将硬实时物理控制与较慢的认知演化分离。安全关键控制环保持确定性和明确边界，而更高层策略可以持续被评估、比较和更新。

## 位置感知

对具身系统来说，位置不是一个孤立的 GPS 坐标，而是一条持续变化的状态流。Timer OS 可以融合全局位置、室内/局部定位、身体姿态与朝向、关节或肢体位置、与人和物体的相对位置、运动轨迹，以及当前位置估计的置信度。

因此，历史位置、当前姿态和目标位置都可以参与认知调度与未来行动规划。

## 具身自我模型

Timer OS 探索一种持续存在的 **Self Model（自我模型）**。它不是由人一次性配置完成，而是可以根据真实世界中的证据不断修正。

自我模型可以包含：

- 身体结构与当前物理状态；
- 标定能力与真实观察到的能力边界；
- 已学习的任务能力与失败模式；
- 当前正在使用的模型/策略版本；
- 对“自己能不能安全完成某件事”的不确定性。

新证据不应立刻覆盖旧认知。不同模型或策略可以并存、持续积累证据、接受测试，最后被保留、替换，或者形成不同环境下的条件策略。

## 第一产品原则：先输入，再打断

Timer OS 首先解决单向问题：

**现实 → Body → 云端认知 → 可持续保存的时间流**

第一阶段目标不是做一个不断主动说话的助手，而是让系统在尽量低打扰的情况下，可靠地重建一个人一天中的高价值信息流。

只有当输入可靠性被验证后，Timer OS 才进一步决定 **是否打断、什么时候打断、用什么方式打断用户**。

具身系统也遵循相同顺序：先建立可靠的状态采集与重建，再逐步启用更高层的自主调度和策略自更新。

## 本仓库公开内容

本仓库仅公开 Timer OS 的 **系统骨架**：

- 架构词汇与模块边界；
- 连续时间流的最小事件协议；
- Body、Brain、Scheduler 和模型 Provider 的抽象接口；
- DeepSeek Provider 的参考接口；
- 具身智能、位置感知和自我模型的高层概念；
- 组件连接方式的最小示例。

目标是在不暴露核心私有实现的前提下，让系统架构可以被讨论、连接和扩展。

## 不开源部分

以下内容明确保持私有：

- Body 硬件设计与固件；
- 音频路由与无缝录音链路实现；
- 说话人/声纹识别实现；
- 位置融合与定位算法；
- 传感器/电机实时调度实现；
- 边缘决策与本地缓存策略；
- YIdui 的认知状态、自我模型更新算法；
- 知识、模型与策略的冲突/更新机制；
- 策略演化和验证逻辑；
- 注意力/打断调度策略；
- 生产云端编排、Prompt、评分和策略逻辑；
- 私有数据集、用户数据与评估数据。

公开接口可以描述这些模块如何连接，但不公开其内部实现方式。
